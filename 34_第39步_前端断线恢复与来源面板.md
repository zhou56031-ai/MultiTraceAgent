## 1. 场景：刷新不再只能干等通知

小明提交T1后刷新，旧页面只记得“上次在运行”，如果正好错过完成事件就一直等。新页面把T1也保存下来：重新打开时查询服务端账本，拿到最终答案并重新画出来，不重新请求模型。

另外在右侧增加“来源与读取范围”。S1显示可打开的网页地址，F1显示文件名、页数/行数/字符上限。上传后来源仍为空，直到工具真正读取成功才会登记。

## 2. 文件、依赖和修改方式

正式页面仍只有 `learning/api/static/index.html`，不引入Node构建、前端框架或CDN。HTML结构、CSS与JavaScript都在这个文件里；来源面板用安全DOM文本节点创建，不执行模型返回的HTML。

没有新增requirements条目。第38步后端必须先有GET任务接口，否则前端只能提示查询失败。下方片段按顺序替换，旧片段来自改造前实际页面，包含相邻定位文字；片段之间没有省略必须手写的业务代码。

自动浏览器验证脚本在第40步新增，放examples，不要把它放进api/static或让后端导入。

## 3. 先理解新增状态，避免把几个编号混在一起

| 页面字段 | 示例与职责 |
| --- | --- |
| session.id | A，会话编号，上传、WebSocket、图检查点仍用它 |
| session.taskId | T1，本次提问编号，POST前生成，刷新后可找回 |
| message.taskId | 这条问题/答案归属哪次任务，按taskId+role去重 |
| session.sources | 当前任务实际来源元数据，渲染右侧面板 |
| session.recovering | 当前是否已有一次查询在进行，防止重复点按钮并行拉取 |
| session.recoveryTimer | 下一次状态核对的定时器编号，关闭会话时清除 |
| session.submissionPending | POST回执仍未结束时，暂不让查询抢先判断结果 |
| expectedTaskId | 发起GET时记住的编号，GET回来后若已经换了新任务就不覆盖它 |

`taskId`是前端变量名，HTTP/SQLite字段叫`task_id`，发送JSON时明确对应，不是两个不同任务。

## 5. 新函数逐个讲清楚

### renderSources(session)：把登记册画出来

它由render调用，先清空当前面板，再画当前任务的条目。网页条目先用URL对象检查http/https，再创建a标签；文件条目显示scope。条目来自服务端实际工具元数据，不能拿模型随口说的[S99]直接创建来源卡片。

`element`内部使用textContent，因此文件名里的尖括号也只作为文字显示。来源链接另开页面并设置noopener/noreferrer，沿用当前工作台的安全排版方式。

### upsertTaskMessage：找到同一张回单就更新

输入session、taskId、role、content、timestamp。先查该编号和角色的消息：已有则更新正文，没有才append。WebSocket先到一次、HTTP再查到一次，最终仍只显示一条T1的assistant答案。

这不是按答案文本去重。T1与T2的回答即使完全相同，也应该是两轮不同的对话。

### applyTaskRecord：把数据库记录翻译为页面状态

先确保用户问题存在，成功时确保答案存在；然后只对当前taskId更新会话状态与来源。数据库的succeeded对应页面done，interrupted对应“执行已中断”。

关键保护：如果网页刚收到done，而一个较早开始的GET返回旧running快照，不允许把done倒退成running；运行态空sources也不能抹掉刚通过WebSocket收到的来源。

终态动态用taskId+terminal标记避免反复追加，文件列表在确认结束后刷新。它不负责重新执行任务。

### scheduleRecovery / recoverTask：查询，而不是重试提问

scheduleRecovery先清旧定时器，仅当状态仍忙且会话存在时，2.5秒后再查询。recoverTask用recovering/submissionPending防止并行查询或与提交抢跑。

查询先取最近20条任务，恢复各轮问题与成功答案。如果当前taskId不在列表中，再用单任务GET精确查找；因此不把“列表只取20条”误当成“旧任务已被删除”。

HTTP返回后再次比expectedTaskId：如果小明已经开始T2，T1的晚回包就不能改T2状态。手动点“找回任务结果”时，若原编号未找到但有最近任务，可以切到最近记录；完全没有记录则明确提示并解除等待，不自动再次POST。

GET设置10秒超时，POST回执设置15秒超时，避免请求一直挂起把页面锁住。POST仍在等待时也不允许再提交下一轮，防止上一轮回执覆盖新编号。网络查询失败时保留现有内容，运行中的任务继续定时核对。失败只说明此刻查询未成功，不能凭此说模型已失败。

## 6. 原有函数的关键变化

- makeSession / persistSessions / restoreSessions：增存taskId与sources，恢复忙状态时先标“待确认”，再向服务端核对。
- sendTask：连好通知通道后生成T1，把问题和T1立即保存到localStorage，再POST；提交体带task_id。finally只查询，不重复提交。
- connectSession：建立或重建连接后查询账本；连接正常被另一个标签页接管时仍停止争抢WebSocket，但任务核对可继续。
- receiveEvent：事件带的task_id与当前不符则忽略；source_update更新来源，task_result按编号更新答案。
- disposeConnection：连同任务查询定时器一起清理，移除的会话不会在后台不断轮询。

## 7. 用一次断线把所有角色串起来

```text
浏览器保存 A + T1 + 用户问题
→ POST /api/task 带A/T1
→ 后台生成答案并先写账本
→ 完成通知丢失
→ 小明刷新，localStorage恢复A/T1
→ GET任务列表/单任务
→ applyTaskRecord恢复用户问题、答案、来源和done
→ 再点找回只更新同一条答案，不再执行图
```

localStorage仍负责“这台浏览器有哪些会话”，服务端账本负责“这次任务实际是什么状态”。清空浏览器全部记录后，没有自动跨设备会话目录；本步没有增加登录系统或事件历史补发。
